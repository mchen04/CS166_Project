Assumptions — CS 166 Mechanics Shop Phase 2

Schema Changes from Phase 1

- Added specialty VARCHAR(64) to the Mechanic table. The phase 2 spec lists it as input for AddMechanic, so we added it now. The original requirement analysis never mentioned it, which is why it wasn't in phase 1.
- Everything else carries over unchanged — same types, same constraints, same keys.

Index Rationale

- Postgres auto-creates indexes on primary keys, so we only added indexes on columns that show up in JOINs and WHERE clauses across our 10 functions.
- idx_customer_lname on Customer(lname) — InsertServiceRequest searches by last name.
- idx_owns_customer on Owns(customer_id) — looking up which cars a customer owns.
- idx_owns_car on Owns(car_vin) — join path from car back to owner.
- idx_sr_customer on Service_Request(customer_id) — finding service history by customer.
- idx_sr_car on Service_Request(car_vin) — queries 8 and 9 join on car_vin.
- idx_cr_rid on Closed_Request(rid) — checking if a request is already closed.
- idx_cr_mid on Closed_Request(mid) — mechanic workload queries.
- idx_car_year on Car(year) — query 8 filters on year < 1995.
- idx_cr_bill on Closed_Request(bill) — query 6 filters on bill < 100.

Input Validation

- All user input gets validated before it hits the database.
- Names are non-empty, max 32 chars. Phone must match (###)###-#### exactly. Address is non-empty, max 256 chars.
- Year is numeric, 1970-2026. Experience is numeric, 0-100 years. VIN is 1-16 chars and checked for uniqueness.
- Odometer must be a positive integer. Bill must be non-negative. Specialty is non-empty, max 64 chars.
- IDs are non-negative integers — customer, mechanic, and request IDs all start at 0.

App-Level Constraints

These are things the schema can't enforce on its own, so we handle them in the application:

1. Closing date >= request date — CloseServiceRequest checks this before inserting anything.
2. Ownership verification — InsertServiceRequest shows the customer's cars and has them pick one, or add a new one if the car isn't in the system yet.
3. Duplicate close prevention — CloseServiceRequest checks whether the rid already exists in Closed_Request before proceeding.
4. Mechanic existence check — CloseServiceRequest verifies the mechanic ID refers to an actual mechanic before closing.
5. VIN uniqueness — AddCar checks the vin doesn't already exist before inserting.

Query Interpretations

- Q6: date, comment, bill where bill < 100 — straight filter on Closed_Request.
- Q7: customers with more than 20 different cars — COUNT on Owns grouped by customer.
- Q8: cars before 1995 with less than 50k miles — join Car with Service_Request, filter on year and odometer.
- Q9: cars with most pending service requests — we read "pending" as open (not in Closed_Request). The user provides k.
- Q10: customers and total bill — sum of bills across all closed requests per customer, ordered descending.

Prepared Statements

- The GUI (MechanicShopGUI.java) uses PreparedStatements for all database operations to prevent SQL injection.
- The CLI (MechanicShop.java) uses string concatenation with escaping since it follows the UCR template structure.

GUI Design (Extra Credit)

- Built a full Swing GUI with tabbed navigation for all 10 functions.
- Multi-step service request workflow: search customer by last name, pick a car, enter complaint.
- Close request flow with full details lookup before closing.
- Sortable JTable results with row counts for all query panels.
- Pop-up dialogs for adding customers/cars inline during the service request flow.
- SQL log panel, status bar, Nimbus look-and-feel, full input validation with error dialogs.

Data Generation

- 500 customers, 250 mechanics, 800 cars, 800 ownership records.
- 1500 service requests, 1000 closed requests with bills ranging $25-$800.
- 5 customers have 22-25 cars each so query 7 returns results.
- 50 service requests on pre-1995 cars with <50k miles so query 8 returns results.

Known Limitations

- ID generation uses MAX(id)+1 which isn't safe for concurrent inserts. Fine for a single-user class project; a production system would use SERIAL or SEQUENCE.
- No authentication — anyone can close a service request or add records. Out of scope for this project.
